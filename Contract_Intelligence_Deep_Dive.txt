1. EXACT FLAWS IN ingest_to_neo4j.py (WITH LINE REFERENCES)
================================================================================

These are not design criticisms — the design is correct. These are concrete bugs
and missing pieces in the first version that would prevent it working in production.

FLAW 1: EntityResolver dies between ingestion runs (line 80–82)
---------------------------------------------------------------
  The registry is a plain Python dict in memory:
    self._registry: dict[str, dict[str, str]] = defaultdict(dict)

  Every time you restart the script (daily ingestion job, re-processing one
  contract, crash-and-retry), the registry starts empty. Neo4j already has
  "Honeywell Aerospace" as a canonical node from yesterday's run. Today's run
  sees "Honeywell International" fresh, finds no registry match, creates a
  second Party node. The duplicate problem recurs across runs even though
  the in-process logic is correct.

  Fix: Seed the registry at startup from existing Neo4j nodes.
    MATCH (n) RETURN n.canonical_name, labels(n)[0] AS label
  Load all canonical_names into the registry before processing any new files.

FLAW 2: Edge confidence reads a field that GPT never writes (line 381)
----------------------------------------------------------------------
  confidence = float(edge.get("properties", {}).get("confidence", 0.85))

  The extraction schemas in graph_schema_extractor.py and analyze_contracts.py
  never ask GPT to output a "confidence" field. The SYSTEM_PROMPT has no such
  instruction. So this line ALWAYS returns the default 0.85.

  Result: every single edge is treated as 0.85 confidence regardless of
  actual quality. The POSSIBLE_* gating (0.75 threshold) never triggers.
  The confidence gate is completely bypassed.

  Fix: Add "confidence" (0.0–1.0) to the extraction schema and instruct the
  model to self-assess. Or compute it from signals you already have (see
  Section 4). Both are better than a hardcoded default.

FLAW 3: _infer_confidence ignores image quality (lines 322–330)
---------------------------------------------------------------
  def _infer_confidence(self, node: dict, source: str) -> float:
      base = 0.70 if source == "photographed" else 0.90
      has_props = bool(node.get("properties"))
      return base + (0.05 if has_props else 0.0)

  analyze_contracts.py already extracts "image_quality" implicitly (the "notes"
  field often says "image is blurry"). But _infer_confidence never reads it.
  A blurry photographed page gets 0.70 — the same as a crisp photographed page.
  Neither gets treated with appropriate extra skepticism.

  Fix: Add "image_quality": "clear"|"moderate"|"poor" to PER_IMAGE_SCHEMA.
  Pass it through to _infer_confidence and subtract a penalty for "poor".

FLAW 4: src_type / tgt_type defaults to "Unknown" (lines 372–378)
------------------------------------------------------------------
  src_type = next(
      (n["type"] for n in page.get("nodes", []) if n.get("name") == raw_src),
      "Unknown",
  )

  If an edge references an entity that appeared on a different page (cross-page
  edge — very common in multi-page contracts), raw_src won't match any node on
  THIS page. src_type falls back to "Unknown".

  Then merge_edge tries to run:
    MATCH (a:Unknown {canonical_name: $src})

  Neo4j silently finds nothing and writes no edge. No error is raised.
  You lose all cross-page relationship data without knowing it.

  Fix: Maintain a cross-page name→type lookup that persists for the entire
  contract (not just the current page). Build it as pages are processed.

FLAW 5: Vector upsert is a stub — nothing is actually written (line 304)
------------------------------------------------------------------------
  log.debug("Would upsert vector chunk_id=%s neo4j_ids=%s", chunk_id, ...)

  The datapoint dict is constructed but index.upsert_datapoints() is never
  called. The vector store receives zero data. Vector search will return no
  results. The dual-write bridge is never established.

  Fix: Call the actual Vertex AI API. See Section 5 for the real implementation.

FLAW 6: BATCH_SIZE is defined but never used (line 58)
------------------------------------------------------
  BATCH_SIZE = 50  # Neo4j write batch size

  Every node and every edge is written in its own session + transaction:
    with self._driver.session() as s:
        result = s.run(...)

  For a contract with 200 pages × 20 nodes/page = 4,000 nodes, that's 4,000
  separate Neo4j transactions. Each transaction has ~5ms overhead.
  Total overhead: 20 seconds just from transaction management.

  Fix: Accumulate nodes and edges within a page (or across pages) and submit
  them in a single UNWIND batch transaction. See Section 5, Caching, for the
  pattern.

FLAW 7: No cross-run entity registry persistence (structural gap)
-----------------------------------------------------------------
  Related to Flaw 1. There is no mechanism to persist resolved entity aliases
  across ingestion runs. So "Honeywell → Honeywell Aerospace" learned in run 1
  is forgotten by run 2.

  Fix: After each ingestion run, dump the registry to a JSON file or write
  alias relationships (SAME_AS edges) to Neo4j. On the next run, load these
  before processing any contracts.

FLAW 8: No retry queue for partial failures (lines 405–406)
-----------------------------------------------------------
  except Exception as e:
      log.error("Unexpected error on %s page %s: %s", ...)

  If Neo4j writes succeed but the vector upsert fails, we log a warning and
  continue. No retry, no dead-letter queue. The vector store silently drifts
  behind the graph — and you have no way to know which pages are missing from
  the vector index without a full reconciliation scan.

  Fix: On vector upsert failure, publish the failed (chunk_id, contract_id,
  page, neo4j_element_ids) to a Cloud Pub/Sub topic. A separate Cloud Function
  subscriber retries the upsert with exponential backoff.

FLAW 9: MetadataStore column detection is fragile (lines 132–136)
-----------------------------------------------------------------
  id_col = next(
      (c for c in self._df.columns if "contract" in c.lower() and "id" in c.lower()),
      self._df.columns[0],
  )

  If your CSV has multiple columns matching "contract" + "id" (e.g., "General
  Contract ID", "Sales Contract ID", "Legacy Contract ID"), next() picks
  whichever comes first. With no warning. Silently indexes on the wrong column.

  Fix: Require an explicit --id-column argument, or hard-code the column name
  as a constant. Never silently guess the primary key.

FLAW 10: No distributed tracing — impossible to diagnose latency
----------------------------------------------------------------
  There are no OpenTelemetry spans, no Cloud Trace integration, no timing
  instrumentation. If ingestion is slow, you cannot tell whether the bottleneck
  is entity resolution, Neo4j writes, or vector API calls.

  Fix: Add tracer spans around each major step (see Section 6).

FLAW 11: Stats never reach Cloud Monitoring — only in stdout
------------------------------------------------------------
  def print_stats(self):
      log.info("=== Ingestion stats ===")
      for k, v in sorted(self._stats.items()):
          log.info("  %-40s %d", k, v)

  This outputs to stdout. No structured JSON fields, no Cloud Monitoring
  metrics, no Datadog metrics. You cannot alert on "possible_edge_ratio > 30%"
  because the number only exists in a log line, not as a queryable metric.

  Fix: Emit structured JSON logs (see Section 6) and use log-based metrics
  in Cloud Monitoring to turn log fields into alertable gauge/counter metrics.

FLAW 12: Connection pool not configured (line 166)
--------------------------------------------------
  self._driver = GraphDatabase.driver(uri, auth=(user, password))

  Default Neo4j driver pool: 100 connections, 30s acquisition timeout.
  For batch ingestion with BATCH_SIZE=50 concurrent transactions, the defaults
  are fine. But for a production system with concurrent query traffic, you need:
    GraphDatabase.driver(uri, auth=(user, password),
        max_connection_pool_size=50,
        connection_acquisition_timeout=10.0,
        max_transaction_retry_time=30.0)

2. ENTITY RESOLUTION — COMPLETE FIXED DESIGN
================================================================================

THE COMPLETE FLOW (fixing Flaws 1, 7, and cross-page tracking)
---------------------------------------------------------------

Step 1: Startup — seed the registry from existing Neo4j nodes
  On every ingestion run, before processing any file:

    def seed_registry_from_neo4j(self, driver):
        with driver.session() as s:
            result = s.run(
                "MATCH (n) WHERE n.canonical_name IS NOT NULL "
                "RETURN n.canonical_name AS name, labels(n)[0] AS label"
            )
            for record in result:
                norm = self._normalize(record["name"])
                self._registry[record["label"]][norm] = record["name"]
        log.info("Seeded entity registry with %d existing nodes",
                 sum(len(v) for v in self._registry.values()))

Step 2: Per-page processing — cross-page type tracking
  Maintain a contract-level name→type map, updated as each page is processed:

    contract_type_map: dict[str, str] = {}

    for page in pages:
        # Build type map from this page's nodes
        for node in page.get("nodes", []):
            contract_type_map[node["name"]] = node.get("type", "Unknown")

        # When processing edges, look up type from contract_type_map, not just
        # this page's nodes:
        src_type = contract_type_map.get(raw_src, "Unknown")

        # If still Unknown, query Neo4j directly (cross-contract edge)
        if src_type == "Unknown":
            src_type = self._lookup_type_from_neo4j(raw_src, driver) or "Unknown"

Step 3: Post-run — persist aliases to Neo4j
  After each run, write all resolved aliases as SAME_AS edges for the audit trail:

    MERGE (a {canonical_name: $canonical})
    MERGE (b {canonical_name: $alias})
    MERGE (a)-[:SAME_AS {resolved_by: 'entity_resolver', score: $score}]->(b)

Step 4: Human review of borderline merges
  Log all resolutions with score < 0.90 to a review table:
    {raw_name, canonical_name, score, node_type, contract_id, timestamp}
  Weekly review: anything in 0.85–0.89 range that looks wrong can be split.
  Splitting: delete SAME_AS edge, DETACH DELETE the merged node, re-ingest
  the affected contract.

WHAT ENTITY RESOLUTION DOES NOT SOLVE
--------------------------------------
Government entity abbreviations: "USAF", "US Air Force", "United States Air
Force" — these won't fuzzy-match at 0.85. Maintain a manual synonym table:

    SYNONYMS = {
        "USAF": "United States Air Force",
        "DOD": "Department of Defense",
        "NASA": "National Aeronautics and Space Administration",
        "DCMA": "Defense Contract Management Agency",
    }

    def resolve(self, name: str, node_type: str) -> str:
        # Check synonym table first
        canonical = SYNONYMS.get(name.upper(), name)
        # Then do fuzzy matching on the canonical form
        return self._fuzzy_resolve(canonical, node_type)

3a. HOW THE QUERY CLASSIFIER WORKS
------------------------------------

The classifier is a single LLM call made at query time. Its job is NOT to
write Cypher. Its job is:
  (a) Pick exactly one template name from a list
  (b) Extract slot values as JSON

The system prompt for classification:

  """
  You are a query router for a Honeywell contract intelligence system.
  Given a user question, output JSON with two fields:
    - "template": exactly one value from the list below
    - "slots": an object with the parameter values for that template

  Templates:
    contracts_by_party       → slots: {party_name}
    contract_by_id           → slots: {contract_id}
    party_profile            → slots: {party_name}
    milestones_for_contract  → slots: {contract_id}
    deliverables_for_contract → slots: {contract_id}
    standards_for_contract   → slots: {contract_id}
    contracts_by_standard    → slots: {standard_ref}
    milestones_by_party_and_standard → slots: {party_name, standard_ref}
    shared_contracts         → slots: {party_a, party_b}
    cross_doc_references     → slots: {contract_id}
    contract_family          → slots: {contract_id, depth (default 3)}
    contract_ancestry        → slots: {contract_id}
    superseded_contracts     → slots: {contract_id}
    expiring_soon            → slots: {days}
    effective_in_period      → slots: {start_date, end_date}
    milestones_in_period     → slots: {start_date, end_date}
    high_value_contracts     → slots: {amount_usd}
    value_by_party           → slots: {party_name}
    value_by_sbg             → slots: {}
    contracts_by_status      → slots: {status, sbg (optional)}
    contracts_by_type        → slots: {document_type}
    network_summary          → slots: {limit (default 20)}
    standard_frequency       → slots: {limit (default 20)}
    milestone_distribution   → slots: {}
    possible_edge_review     → slots: {node_type (optional), min_confidence}
    unclassified             → slots: {raw_query} (fallback)

  If the question fits no template, use "unclassified" and put the original
  question in slots.raw_query.
  Return only valid JSON. No explanation.
  """

Example classification call:
  User: "What Boeing contracts reference FAR 52.219 and expire this year?"
  Output: {
    "template": "milestones_by_party_and_standard",
    "slots": {"party_name": "Boeing", "standard_ref": "FAR 52.219"}
  }
  ← The system fills in the Cypher template with these slots and executes it.
  ← GPT never writes Cypher. GPT only classifies and extracts values.

Execution flow:
  1. query_text → classification LLM call (~200ms, can be cached by query hash)
  2. template_name + slots → look up in TEMPLATE_REGISTRY dict
  3. Slot validation (type check, required fields present)
  4. Execute Cypher with driver.session().run(template["cypher"], **slots)
  5. Serialize result → pass to final answer LLM with original question
  6. Log: {query_text, template, slots, result_count, latency_ms, cache_hit}


3b. THE 8 TEMPLATE CATEGORIES — FULL COVERAGE
----------------------------------------------

===== CATEGORY A: ENTITY LOOKUP =====
Purpose: "Find me things by name"
Signal words: company names, "involving", "with", "by", contract numbers

A1. contracts_by_party
  Natural language: "Find all Boeing contracts", "What contracts involve Airbus?",
                    "Show me everything with the US Air Force"
  Slots: party_name (string, partial match)

  MATCH (p:Party)
  WHERE p.canonical_name =~ ('(?i).*' + $party_name + '.*')
  MATCH (p)<-[:PARTY_TO]-(c:Contract)
  RETURN c.contract_id,
         c.sales_contract_effective_date,
         c.sales_contract_expiration_date,
         c.sales_contract_status,
         c.sales_contract_or_amendment_value_usd,
         c.general_contract_sbgs
  ORDER BY c.sales_contract_expiration_date
  Required index: CREATE INDEX party_canonical FOR (p:Party) ON (p.canonical_name)

A2. contract_by_id
  Natural language: "Pull up contract HC-2023-001", "Show me contract number X",
                    "Look up HC2022-094"
  Slots: contract_id (string, exact or partial)

  MATCH (c:Contract)
  WHERE c.contract_id = $contract_id OR c.contract_id CONTAINS $contract_id
  OPTIONAL MATCH (c)-[:PARTY_TO]->(p:Party)
  OPTIONAL MATCH (c)-[:HAS_MILESTONE]->(m:Milestone)
  OPTIONAL MATCH (c)-[:REFERENCES_STANDARD]->(s:Standard)
  OPTIONAL MATCH (c)-[:HAS_DELIVERABLE]->(d:Deliverable)
  RETURN c,
         collect(DISTINCT p.canonical_name) AS parties,
         collect(DISTINCT {label: m.label, date: m.date, value: m.value}) AS milestones,
         collect(DISTINCT s.name) AS standards,
         collect(DISTINCT d.name) AS deliverables
  Required index: CREATE INDEX contract_id_idx FOR (c:Contract) ON (c.contract_id)

A3. party_profile
  Natural language: "Tell me everything about Boeing across all our contracts",
                    "What's our relationship with Raytheon?", "Boeing profile"
  Slots: party_name

  MATCH (p:Party)
  WHERE p.canonical_name =~ ('(?i).*' + $party_name + '.*')
  MATCH (p)<-[:PARTY_TO]-(c:Contract)
  OPTIONAL MATCH (c)-[:HAS_MILESTONE]->(m:Milestone)
  RETURN p.canonical_name AS party,
         count(DISTINCT c) AS total_contracts,
         sum(toFloat(c.sales_contract_or_amendment_value_usd)) AS total_value_usd,
         collect(DISTINCT c.sales_contract_status) AS statuses,
         collect(DISTINCT c.general_contract_sbgs) AS sbgs,
         count(m) AS total_milestones,
         min(date(c.sales_contract_effective_date)) AS earliest_contract,
         max(date(c.sales_contract_expiration_date)) AS latest_expiry


===== CATEGORY B: RELATIONSHIP TRAVERSAL =====
Purpose: "What is connected to this entity?"
Signal words: "milestones", "deliverables", "standards", "requirements",
              "references", "sections"

B1. milestones_for_contract
  Natural language: "What milestones are in contract X?",
                    "Show me the schedule for HC-2023-001",
                    "When are the CDR and PDR for contract X?"
  Slots: contract_id

  MATCH (c:Contract)-[:HAS_MILESTONE]->(m:Milestone)
  WHERE c.contract_id = $contract_id
  RETURN m.label, m.date, m.value,
         m._extraction_confidence AS confidence
  ORDER BY m.date ASC

B2. deliverables_for_contract
  Natural language: "What are the deliverables for contract X?",
                    "What does Honeywell owe under HC-2023-001?"
  Slots: contract_id

  MATCH (c:Contract)-[:HAS_DELIVERABLE]->(d:Deliverable)
  WHERE c.contract_id = $contract_id
  RETURN d.name, d.properties, d._extraction_confidence

B3. standards_for_contract
  Natural language: "What FAR clauses does contract X reference?",
                    "Which standards apply to HC-2023-001?",
                    "What regulatory requirements are in contract X?"
  Slots: contract_id

  MATCH (c:Contract)-[:REFERENCES_STANDARD]->(s:Standard)
  WHERE c.contract_id = $contract_id
  RETURN s.name, s.properties
  ORDER BY s.name

B4. contracts_by_standard
  Natural language: "Which contracts reference FAR 52.219?",
                    "Find all contracts with DFARS 252.204",
                    "Which contracts mention the Buy American Act?"
  Slots: standard_ref (partial string match)

  MATCH (c:Contract)-[:REFERENCES_STANDARD]->(s:Standard)
  WHERE s.name CONTAINS $standard_ref
  RETURN c.contract_id,
         c.sales_contract_company_name,
         c.sales_contract_status,
         s.name AS matched_standard
  ORDER BY c.contract_id
  Required index: CREATE TEXT INDEX standard_name FOR (s:Standard) ON (s.name)

B5. requirements_for_contract
  Natural language: "What are the requirements in contract X?",
                    "List all obligations under HC-2023-001"
  Slots: contract_id

  MATCH (c:Contract)-[:CONTAINS_REQUIREMENT]->(r:Requirement)
  WHERE c.contract_id = $contract_id
  RETURN r.name, r.properties, r._extraction_confidence
  ORDER BY r.name

B6. sections_for_contract
  Natural language: "What sections are in contract X?",
                    "Show me the table of contents for HC-2023-001"
  Slots: contract_id

  MATCH (c:Contract)-[:HAS_SECTION]->(sec:Section)
  WHERE c.contract_id = $contract_id
  RETURN sec.name, sec.properties
  ORDER BY sec.name


===== CATEGORY C: MULTI-HOP / CROSS-ENTITY =====
Purpose: "Find things at the intersection of two conditions"
Signal words: "AND", "both", "where X and Y", "that also", "referencing...AND"

C1. milestones_by_party_and_standard
  Natural language: "What milestones exist in Boeing contracts referencing FAR 52.219?",
                    "Show me CDR dates for Raytheon contracts with DFARS subcontracting"
  Slots: party_name, standard_ref

  MATCH (p:Party)<-[:PARTY_TO]-(c:Contract)-[:REFERENCES_STANDARD]->(s:Standard)
  WHERE p.canonical_name =~ ('(?i).*' + $party_name + '.*')
    AND s.name CONTAINS $standard_ref
  MATCH (c)-[:HAS_MILESTONE]->(m:Milestone)
  RETURN c.contract_id, p.canonical_name,
         m.label, m.date, m.value, s.name

C2. shared_contracts_between_parties
  Natural language: "Find contracts where Boeing and Honeywell are both involved",
                    "Which contracts have both the US Air Force and Northrop Grumman?"
  Slots: party_a, party_b

  MATCH (pa:Party)<-[:PARTY_TO]-(c:Contract)-[:PARTY_TO]->(pb:Party)
  WHERE pa.canonical_name =~ ('(?i).*' + $party_a + '.*')
    AND pb.canonical_name =~ ('(?i).*' + $party_b + '.*')
  RETURN c.contract_id,
         pa.canonical_name AS party_a,
         pb.canonical_name AS party_b,
         c.sales_contract_status,
         c.sales_contract_or_amendment_value_usd

C3. high_value_contracts_by_party
  Natural language: "Which Boeing contracts are worth more than $10M?",
                    "Show me Airbus contracts over $5 million"
  Slots: party_name, amount_usd

  MATCH (p:Party)<-[:PARTY_TO]-(c:Contract)
  WHERE p.canonical_name =~ ('(?i).*' + $party_name + '.*')
    AND toFloat(c.sales_contract_or_amendment_value_usd) > $amount_usd
  RETURN c.contract_id,
         toFloat(c.sales_contract_or_amendment_value_usd) AS value_usd,
         c.sales_contract_expiration_date
  ORDER BY value_usd DESC

C4. active_contracts_expiring_for_party
  Natural language: "Which Boeing contracts expire in the next 90 days?",
                    "What's coming up for renewal with Raytheon?"
  Slots: party_name, days

  MATCH (p:Party)<-[:PARTY_TO]-(c:Contract)
  WHERE p.canonical_name =~ ('(?i).*' + $party_name + '.*')
    AND c.sales_contract_status = 'Active'
    AND date(c.sales_contract_expiration_date) >= date()
    AND date(c.sales_contract_expiration_date) <= date() + duration({days: $days})
  RETURN c.contract_id,
         c.sales_contract_expiration_date,
         duration.between(date(), date(c.sales_contract_expiration_date)).days AS days_remaining
  ORDER BY c.sales_contract_expiration_date

C5. cross_document_references
  Natural language: "What does contract X reference?",
                    "Which contracts are linked to HC-2023-001?",
                    "Find all documents referenced by this contract"
  Slots: contract_id

  MATCH (c:Contract {contract_id: $contract_id})
  OPTIONAL MATCH (c)-[r1:RELATED_TO]->(linked1)
  OPTIONAL MATCH (c)-[r2:SUPERSEDES]->(linked2)
  OPTIONAL MATCH (c)<-[r3:PARENT_OF]-(parent)
  RETURN c.contract_id,
         collect(DISTINCT {type: 'RELATED_TO', id: linked1.contract_id}) AS related,
         collect(DISTINCT {type: 'SUPERSEDES', id: linked2.contract_id}) AS supersedes,
         collect(DISTINCT {type: 'PARENT', id: parent.contract_id}) AS parents


===== CATEGORY D: CONTRACT LINEAGE =====
Purpose: "Show me the history / hierarchy of a contract"
Signal words: "parent", "child", "supersede", "replace", "legacy", "family",
              "version", "amendment", "master agreement"

D1. contract_family
  Natural language: "Show me the contract family of HC-2019-001",
                    "What contracts came from master agreement X?",
                    "Show me all amendments and children under HC-2019-001"
  Slots: contract_id, depth (default 3)

  MATCH path = (root:Contract {contract_id: $contract_id})
               -[:PARENT_OF|SUPERSEDES*1..$depth]->(descendant)
  RETURN [n IN nodes(path) | n.contract_id] AS lineage_chain,
         length(path) AS depth,
         last(nodes(path)).sales_contract_status AS leaf_status

D2. contract_ancestry
  Natural language: "What is the parent contract of HC-2023-001?",
                    "Find the master agreement that HC-2023-001 came from",
                    "What's the history above this contract?"
  Slots: contract_id

  MATCH path = (child:Contract {contract_id: $contract_id})
               <-[:PARENT_OF*1..5]-(ancestor)
  RETURN [n IN nodes(path) | n.contract_id] AS ancestry_chain,
         length(path) AS levels_up

D3. superseded_contracts
  Natural language: "What contracts did HC-2023-001 replace?",
                    "Find the legacy version of this contract",
                    "What was the previous contract before HC-2023-001?"
  Slots: contract_id

  MATCH (c:Contract {contract_id: $contract_id})-[:SUPERSEDES]->(old)
  RETURN old.contract_id,
         old.sales_contract_status,
         old.sales_contract_expiration_date,
         old.sales_contract_or_amendment_value_usd

D4. full_lineage_tree
  Natural language: "Show me the complete contract tree for HC-2019-001",
                    "Give me the full hierarchy — parents AND children"
  Slots: contract_id

  MATCH (root:Contract {contract_id: $contract_id})
  OPTIONAL MATCH up_path = (root)<-[:PARENT_OF*1..3]-(ancestor)
  OPTIONAL MATCH down_path = (root)-[:PARENT_OF|SUPERSEDES*1..3]->(descendant)
  RETURN
    [n IN nodes(up_path) | n.contract_id] AS ancestors,
    root.contract_id AS root,
    [n IN nodes(down_path) | n.contract_id] AS descendants


===== CATEGORY E: TIME-BASED =====
Purpose: "What's happening when?"
Signal words: "expiring", "due", "next", "between", "in the next X days",
              "by", "before", "after", "Q1", "quarter", "year"

E1. expiring_soon
  Natural language: "Contracts expiring in the next 90 days",
                    "What's coming up for renewal?", "What expires before Q2?"
  Slots: days (integer)

  MATCH (c:Contract)
  WHERE c.sales_contract_status = 'Active'
    AND date(c.sales_contract_expiration_date) >= date()
    AND date(c.sales_contract_expiration_date) <= date() + duration({days: $days})

4a. SCORING MODEL
------------------

Final score = base × quality_modifier, capped to [0.0, 1.0]

Base score (from source type):
  PDF native text (clean machine-readable text):  0.90
  Photographed (image → GPT vision):              0.70

Quality modifiers (multiplicative, applied in order):
  Image is "poor" (blurry, rotated, low contrast):   × 0.80
  Image is "moderate":                                × 0.95
  Image is "clear":                                   × 1.00
  Node has at least one non-empty property value:     × 1.05
  Node has zero property values (name only):          × 0.95
  GPT self-assessment < 0.6 (if you add it):          × 0.85
  GPT self-assessment >= 0.8:                         × 1.05

Examples:
  PDF text, has properties:                0.90 × 1.00 × 1.05 = 0.945 → hard edge
  Photographed, clear image, has props:   0.70 × 1.00 × 1.05 = 0.735 → hard edge
  Photographed, moderate image, no props: 0.70 × 0.95 × 0.95 = 0.632 → POSSIBLE_*
  Photographed, poor image:               0.70 × 0.80 × 0.95 = 0.532 → POSSIBLE_*
  Photographed, poor, no props:           0.70 × 0.80 × 0.95 = 0.532 → POSSIBLE_*

Gates:
  >= 0.85   → Hard edge, confidence stored as property (for filtering)
  0.75–0.84 → Hard edge, confidence property (queryable but not hidden)
  0.60–0.74 → POSSIBLE_{RELATION} edge (excluded from default traversals)
  < 0.60    → Do not write to graph; publish to Cloud Pub/Sub for human review

Updated _infer_confidence (replaces the version in ingest_to_neo4j.py):

  def _infer_confidence(self, node: dict, source: str, image_quality: str = "clear") -> float:
      base = 0.70 if source == "photographed" else 0.90

      quality_mult = {"clear": 1.00, "moderate": 0.95, "poor": 0.80}.get(image_quality, 0.95)

      props = node.get("properties") or {}
      has_values = any(v not in (None, "", []) for v in props.values())
      prop_mult = 1.05 if has_values else 0.95

      gpt_confidence = node.get("gpt_confidence")  # new field in extraction schema
      if gpt_confidence is not None:
          gpt_mult = 1.05 if gpt_confidence >= 0.8 else (0.85 if gpt_confidence < 0.6 else 1.00)
      else:
          gpt_mult = 1.00

      score = base * quality_mult * prop_mult * gpt_mult
      return max(0.0, min(1.0, round(score, 3)))

5. CACHING — COMPLETE FOUR-LAYER IMPLEMENTATION

LAYER 1: NEO4J PAGE CACHE (ZERO CODE, JUST CONFIG)
----------------------------------------------------
This is Neo4j's internal memory management. Pages of the graph store that are
accessed frequently stay in RAM. The page cache is the single biggest latency
lever for graph queries.

Configuration in neo4j.conf:
  # Set to 50–70% of available RAM on the Neo4j host
  # For a server with 16GB RAM dedicated to Neo4j:
  server.memory.pagecache.size=8g

  # Heap (for Cypher query execution and transaction state)
  server.memory.heap.initial_size=2g
  server.memory.heap.max_size=4g

How to check if it's working:
  # At the Neo4j browser:
  CALL dbms.queryJmx("org.neo4j:instance=kernel#0,name=Page cache")
  YIELD attributes
  RETURN attributes["Hit Ratio"].value AS hit_ratio
  # Target: > 0.95 (95% of reads served from RAM)

What hurts page cache performance:
  - Re-ingesting large batches pushes new pages in, evicting hot query pages
  - Solution: ingest during off-peak hours, or use a separate Neo4j instance
    for reads (read replica) vs writes (primary)


LAYER 2: REDIS / CLOUD MEMORYSTORE (APPLICATION QUERY CACHE)
--------------------------------------------------------------
Cache the RESULT of executing a Cypher template. Key = hash of
(template_name + sorted slots). TTL = based on how recently the contracts
in the result set were last updated.

On GCP: Use Cloud Memorystore for Redis (managed, no ops overhead).
  gcloud redis instances create contract-cache \
    --size=2 \
    --region=us-central1 \
    --redis-version=redis_7_0

Full implementation:

  import redis
  import hashlib
  import json
  from datetime import datetime

  redis_client = redis.Redis(
      host=os.environ["REDIS_HOST"],  # Cloud Memorystore IP
      port=6379,
      decode_responses=True,
  )

  def cache_key(template_name: str, slots: dict) -> str:
      payload = template_name + json.dumps(slots, sort_keys=True)
      return "cq:" + hashlib.sha256(payload.encode()).hexdigest()[:16]

  def ttl_for_result(result: list[dict]) -> int:
      """
      TTL in seconds based on how recently the returned contracts were ingested.
      Fresh contracts (< 1 hour old) get a short TTL so changes propagate quickly.
      Stale contracts (> 7 days unchanged) get a long TTL.
      """
      now = datetime.utcnow()
      most_recent_ingest = None
      for row in result:
          ts = row.get("_last_ingested")
          if ts:
              t = datetime.fromisoformat(ts)
              if most_recent_ingest is None or t > most_recent_ingest:
                  most_recent_ingest = t

      if most_recent_ingest is None:
          return 3600  # default: 1 hour

      age_hours = (now - most_recent_ingest).total_seconds() / 3600
      if age_hours < 1:
          return 300     # very fresh: cache for 5 minutes
      elif age_hours < 24:
          return 1800    # recent: cache for 30 minutes
      elif age_hours < 168:  # 7 days
          return 7200    # stale: cache for 2 hours
      else:
          return 86400   # old: cache for 24 hours

  def execute_template(template_name: str, slots: dict, driver) -> list[dict]:
      # Skip cache for time-sensitive templates
      NO_CACHE_TEMPLATES = {"expiring_soon", "milestones_in_period",
                            "recently_modified_contracts", "possible_edge_review"}
      if template_name in NO_CACHE_TEMPLATES:
          return _run_cypher(template_name, slots, driver)

      key = cache_key(template_name, slots)
      cached = redis_client.get(key)
      if cached:
          metrics.increment("query.cache_hit", tags=[f"template:{template_name}"])
          return json.loads(cached)

      result = _run_cypher(template_name, slots, driver)
      ttl = ttl_for_result(result)
      redis_client.setex(key, ttl, json.dumps(result))
      metrics.increment("query.cache_miss", tags=[f"template:{template_name}"])
      return result

CACHE INVALIDATION ON INGESTION:
When a contract is re-ingested, invalidate all cache entries that mention
that contract_id. Use Redis key patterns:

  def invalidate_contract(contract_id: str):
      # Option A: store a reverse index of contract_id → cache keys
      cache_keys = redis_client.smembers(f"cq:contract:{contract_id}")
      if cache_keys:
          redis_client.delete(*cache_keys)
          redis_client.delete(f"cq:contract:{contract_id}")

  # When caching a result, register which contracts are in it:
  def register_cache_entry(key: str, result: list[dict]):
      contract_ids = {row.get("contract_id") for row in result if row.get("contract_id")}
      for cid in contract_ids:
          redis_client.sadd(f"cq:contract:{cid}", key)
          redis_client.expire(f"cq:contract:{cid}", 86400)  # cleanup TTL

Cache the top-k vector search results for a given query. The embedding

  def cached_vector_search(query_text: str, top_k: int = 5) -> list[dict]:
      # Embed the query

      if cached:

      # Call Vertex AI

6a. IS DATADOG ALLOWED ON GCP?
--------------------------------

SHORT ANSWER: Yes. Datadog runs on GCP and there is no GCP restriction on it.

Technically: Datadog is a third-party SaaS. You install the Datadog Agent on
your GCP compute resources (GCE VMs, GKE pods, Cloud Run). The agent collects
metrics and sends them to Datadog's platform. GCP has no policy against this.

Datadog's GCP integration also works in the other direction: Datadog can pull
metrics and logs FROM GCP services (Vertex AI, Cloud Datastore, GCS, etc.)

      span.set_attribute("contract.source", source)
